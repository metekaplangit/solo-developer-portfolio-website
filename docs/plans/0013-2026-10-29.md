## A — A screenshot gallery keeps the picture you were on when the window narrows or the phone turns upright

bump: patch. screen: @sole-focus @magic-notes.

- Outcome: on Sole Focus and Magic Notes, a gallery resting on any picture is still on that picture after the track changes size, in every engine, with the counter and dots agreeing.
- Reproduction (hunt-project 0001, C5): in Playwright WebKit 26.4 open `/apps/sole-focus/` at 932×900; scroll the gallery into view; click dot 3; wait 2.5 s; set the viewport to 430×900; wait 2.5 s. Expected slide 3, counter 3. Observed slide 5 of 5, counter 5. Also 844 → 390 (slide 5) and 1440 → 390 (Sole Focus slide 5, Magic Notes slide 6). Chrome 156 never moves.
- Cause: `initGallery` in `src/components/ScreenshotShowcase.astro` (around lines 517–590) has no size-change handling and trusts the browser to keep the snapped slide. WebKit keeps the old pixel offset, clamps it to the narrower track's end and snaps there whenever (slide − 1) × old width exceeds (slides − 1) × new width.
- Chain: the counter and dots follow the scroll (`scroll` listener, `Math.round(track.scrollLeft / track.clientWidth)`), so they agree with the wrong slide. Both slide galleries share `initGallery`. The phone rail (`initPhones`) pages by view and is not affected.
- Acceptance: the reproduction above, and every resize case of the hunt (1440 ↔ 390, 1440 → 1000, 1180 ↔ 820, 932 ↔ 430, 844 → 390, by dot and by arrow), ends on the slide it started on, counter and dot matching, in WebKit and Chrome; the correction is instant, never a visible slide across the rail.
- Touches: `src/components/ScreenshotShowcase.astro` (`initGallery`), `tests/screens/site.spec.ts`.
- Must keep working: arrows, dots, keys and counter on both galleries, including the dot marker that rides the scroll timeline; swiping and trackpad scrolling; the Waypost Words phone rail.
- Proof: `npm run headless`; `node scripts/rendered.mjs @sole-focus @magic-notes`; `node scripts/probe/hunt-probe.mjs drive --engine webkit` with its gallery steps clean.
- Prior art: re-pin by slide, not by offset — web.dev's `scrollBy(0,0)` does not guarantee the same element; the phone rail already watches its size through a ResizeObserver (plan 0012 B). Avoid: a window `resize` listener alone (the track can change size without one — plan 0012 B's lesson); a smooth correction (`scroll-behavior: smooth` on `.track` would animate the jump across the rail); `scrollBy(0,0)`. Constraint: premium first, built efficiently — no work while nothing changes size; the scroll handler must not adopt the clamped position before the re-pin lands.
- Cheap test (Every fix leaves 1 cheap test, so the same problem never returns):

  - It checks the rule the bug broke — every route, item or input that rule covers — and what the user sees: never 1 example, an input, or the code's own constant.
  - Logic that lives in screen code gets a cheap test of that logic, even when a screen test also stays.

  Here: the screen suite runs Chrome, which re-snaps by itself, so the test reproduces WebKit's behaviour in Chrome — snapping switched off on the track through its style property (the CSP blocks an injected `<style>`), so the browser keeps the old offset as WebKit does — and checks both galleries rest on a middle and a late slide, narrow, and stay on that slide with the counter matching. It must be seen red on the unfixed code.
- Most likely wrong: WebKit may deliver the clamp's scroll event before the size callback, so the scroll handler adopts the wrong slide first; the WebKit drive is what decides.
