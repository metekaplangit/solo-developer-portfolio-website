# Task Card — STEP-0079

- **ID:** STEP-0079
- **Type:** fix (performance)
- **One outcome:** The product identity icon loads eagerly wherever it renders inside the first screen, and stays lazy everywhere else.
- **Feedback:** owner, 2026-08-04 — a UI polish pass asking for the interface to be "better, faster, optimized, and performant".
- **Why now:** STEP-0077 put this icon into the product band a day earlier. `ProductAvatar` has hardcoded `loading="lazy"` since it was written, when it only ever appeared far down a page; that assumption is now false on three surfaces.
- **What it actually was:** `ProductAvatar.astro:56` set `loading="lazy"` unconditionally. Measured in a headless browser, the icon renders at **165px** from the top of a product page at 390px (153px at 1440px), at **181px** on a policy page, and at **399px** on the catalog at 768px — all inside the first screen.
- **Prior art:** a lazy image is skipped by the browser's preload scanner, so it is not queued until layout reaches it. web.dev measures pages that do not lazy-load their above-fold image at 79% "good" LCP against 52% for pages that do. ([web.dev, *The performance effects of too much lazy loading*](https://web.dev/articles/lcp-lazy-loading), checked 2026-08-04.)
- **Weighed, not adopted:** that 79%-vs-52% figure is about the **LCP element**, and these icons are not it — STEP-0053 already made the lead shot eager with `fetchpriority="high"`. The article justifies the direction, not the size of the win, so the number on this card is the one measured here and not the one borrowed from it.
- **Avoid:** setting `fetchpriority="high"` alongside. That hint is meaningful on one image per page and belongs to the LCP element; a 56px icon competing for it would take priority away from the thing that decides the paint (the reasoning STEP-0053 recorded). Avoid too: making the avatar eager everywhere — it also renders in `ProductCard` on the home catalog grid, below the fold, where lazy is right.
- **Approach:** one `eager` prop on `ProductAvatar`, mirroring the prop `ProductBand` already carries for the lead shot, defaulting to lazy. Set at the three above-the-fold call sites: the product detail header, the policy header, and the product band — where the band passes its own `eager` flag straight through, so the icon and the lead shot beside it cannot disagree about which screen they are on. `ProductCard` keeps the default.
- **Acceptance criteria:** (1) no product icon inside the first screen carries `loading="lazy"` on any route at any width. (2) The catalog's second band and the home card grid stay lazy. (3) The icon's load time is measured before and after on a throttled cold load, and whatever it says is what the card records. (4) No `fetchpriority` is added. (5) No layout shift — the avatar already declares width and height.
- **Non-goals:** the gallery slides, the LCP image (STEP-0053), and image format (settled measured-and-rejected in STEP-0058).
- **Files:** `src/components/ProductAvatar.astro`, `src/components/ProductBand.astro`, `src/components/PolicyArticle.astro`, `src/pages/apps/[slug].astro`, `docs/STATUS.md`, `docs/ROADMAP.md`, `docs/CHECKPOINTS.md`, `docs/CHANGELOG.md`.
- **Evidence method:** the built output read for `loading` per image, plus a cold-profile load on a throttled connection (150ms latency, 1.6Mbps, 4× CPU), 5 runs per route, median of the icon's `responseEnd`.
- **Proof classification:** machine-verifiable measurement.
- **Rollback/containment:** `git revert -m 1`. One prop with a safe default; every unset call site behaves exactly as before.
- **Required checks:** `npm run build`; `npm run check`; `npm test`; `npm run test:dist`; `python3 scripts/validate-governance.py`.
- **Issue links:** none. Owner feedback, 2026-08-04.
- **Evidence after completion:** Gates: build exit 0 (10 pages), check exit 0 with 0/0/0, 111/111 unit, 14/14 dist, validator 44/44.
