# Task Card — STEP-0055

- **ID:** STEP-0055
- **Type:** feature (UI polish — scroll-driven motion)
- **One outcome:** The scroll-reveal actually runs, and siblings in a group arrive in sequence instead of all at once.
- **Why now:** Second of three motion cards. The reveal was the site's only scroll-driven effect and was applied identically to every element that carried it.
- **The headline finding — the reveal had never run.** Measured 2026-08-01 on the built site: `.reveal` computed `animation-name: none`, `animation-timeline: auto`, **zero running animations**. Cause: written as `animation: reveal-rise linear both;` followed by `animation-timeline: view();`, the build's minifier folded the two into `animation: linear both reveal-rise view()`. A timeline is **not** a legal component of the `animation` shorthand, so the browser dropped the whole declaration. It shipped invisibly because the effect's designed fallback is "content fully visible", which is exactly what everyone saw. Fixed by using longhand properties, which the minifier has nothing to fold.
- **Acceptance criteria:** (1) Every `.reveal` computes a real `animation-name` and a `view()` timeline. (2) Siblings in a group have distinct, increasing ranges, capped. (3) Content stays fully visible where the effect does not run and under `reduce` — the `DESIGN.md` standing rule. (4) No JavaScript added. (5) 0 horizontal overflow, rail equality unchanged.
- **Design decision — stagger by shifting the view range, not by `animation-delay`.** A scroll-driven animation has no clock, so a delay does nothing. Offsetting each sibling's own entry range is the equivalent and is what makes the second item begin a beat after the first as the group crosses the fold.
- **Design decision — count with `of .reveal`.** A plain `:nth-child(2)` matched the **first** figure of the home mosaic, because a visually-hidden `h2` labels the group and `nth-child` counts every sibling regardless of class. `:nth-child(2 of .reveal)` counts only revealed siblings.
- **Capped at four steps:** the fifth sibling and beyond share the last offset, so a long list never leaves its tail crawling.
- **Prior art:** scroll-driven CSS animations are supported in Safari 26+ and Chrome/Edge 115+, Firefox partial behind a flag — ~84% globally as of mid-2026 (WebKit, *WebKit Features in Safari 26.0*; caniuse; checked 2026-07-31). The existing `@supports (animation-timeline: view())` gate is kept, so the remainder see static, fully visible content.
- **Avoid:** the `animation` shorthand anywhere a timeline is involved — that is the bug above. Also avoid `IntersectionObserver` for this: measured the same week, IO callbacks do not fire in the local browser harness at all, which makes anything built on it unprovable here (STEP-0051).
- **Attempted and removed — the header "settle".** A scroll-driven fade of the nav's hairline over the first 120px. The timeline attached (a real `ScrollTimeline` came back from `getAnimations()`) but its progress stayed `null` and the computed border never moved, across three attempts: a bare `scroll()`, then longhand properties, then an explicit `scroll(root block)` after checking MDN's `scroll()` reference. Unprovable in the harness available on this machine, and **new motion that cannot be shown to work is not motion to ship**. Removed, with a note in `Nav.astro` telling the next person not to re-attempt it blindly. The header keeps the hairline it has always had.
- **Non-goals:** new reveal targets; the gallery; page transitions (STEP-0056).
- **Files:** `src/styles/global.css` (`.reveal` longhands + stagger), `src/components/Nav.astro` (the removal note).
- **Evidence method:** computed `animation-name` / `animation-timeline` / `animation-range` and `getAnimations().length` per revealed element across three routes; built-CSS inspection to confirm the shorthand is gone.
- **Proof classification:** machine-verifiable (measured), with one item recorded **unproven** below.
- **Required checks:** `npm run build`; `npm run check`; `npm test`; validator; deploy-time Lighthouse a11y gate (≥0.95).
- **Unproven, stated rather than rounded up:** the reveal's *visible* motion. Scroll-timeline progress does not report in the harness here (the same limitation that removed the header effect), so what is proved is that the animation is attached and live where it was previously `none` — a definite repair — not that it looks right in motion. **Verify on the live page after deploy**, the way the gallery counter was in STEP-0051.
