# Task Card — STEP-0065

- **ID:** STEP-0065
- **Type:** fix (security control)
- **One outcome:** Every built page carries a Content-Security-Policy that blocks a script the site did not build.
- **Feedback:** AUDIT-0010 (whole-project evaluation, 2026-08-01). Security scored 62, the lowest area.
- **Why now:** `grep -rl "Content-Security-Policy" dist public src` found nothing, and `curl -sI https://metkapstudio.com/` returned no CSP, no `referrer-policy`, no `x-content-type-options`. `docs/SECURITY.md` states the control "no third-party script embeds" — and AUDIT-0009 found Cloudflare injecting `static.cloudflareinsights.com/beacon.min.js` into every **live** page against exactly that control. It went unnoticed because nothing in this repository can see the edge. The beacon is gone (verified 2026-08-01: the live page has one `<script>`, JSON-LD), but the same thing can happen again from any dashboard setting. This is the one control that makes it break visibly.
- **Prior art:** Astro has **stable** CSP under `security.csp` since 6.0.0 — confirmed against the installed `astro@7.1.6` at `node_modules/astro/dist/types/public/config.d.ts`, not the experimental flag it shipped as in 5.9. It emits the `<meta>` element and auto-generates hashes for every bundled script and style ([Astro CSP docs](https://docs.astro.build/en/reference/experimental-flags/csp/), read 2026-08-01).
- **Avoid:** hand-writing the meta tag and hashing by hand. `dist` ships one 1093-byte inline module (`src/components/ScreenshotShowcase.astro`) and zero external `.js` files; a hand-maintained hash stops matching the first time that script is edited, and the failure mode is the gallery quietly not working.
- **Avoid:** expecting `frame-ancestors` or `report-uri` to work. Both are ignored inside a meta element per the CSP spec, and `Content-Security-Policy-Report-Only` cannot be used in one ([MDN CSP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP); [OWASP CSP cheat sheet](https://cheatsheetseries.owasp.org/cheatsheets/Content_Security_Policy_Cheat_Sheet.html), read 2026-08-01). It ships enforcing or not at all.
- **Approach:** enable `security.csp` and add the directives Astro does not own — `default-src`, `img-src`, `font-src`, `connect-src`, `frame-src`, `object-src`, `form-action`, `base-uri`. Astro supplies `script-src` and `style-src` with real hashes.
- **Design decision — a meta tag, knowingly second-best.** Server headers are always preferable and the sources say so; GitHub Pages cannot set them. The residual gap is a parse-time race where a browser may run script before the policy takes effect. Stated rather than discovered later.
- **Design decision — `style-src-attr 'unsafe-inline'`, and only that.** Found by the probe, not by reading. See the evidence below.
- **Design decision — Cloudflare Transform Rules are named, not attempted.** Real headers are a dashboard setting and belong to the account holder.
- **Compatibility checked:** Astro's CSP does not support its `ClientRouter`. Not a problem here — `src/styles/global.css` already uses the native `@view-transition` at-rule and records why `ClientRouter` was deliberately rejected. That is precisely the migration Astro's own note recommends, done before this card existed.
- **Acceptance criteria:** (1) Every built page contains a CSP meta element. (2) All 8 routes load in a headless browser with zero CSP violations. (3) The gallery script still runs and still advances. (4) An injected third-party script is refused. (5) `--hue` still resolves to the product's colour, not the default.
- **Non-goals:** Cloudflare dashboard changes; report-only mode (impossible in a meta tag).
- **Files:** `astro.config.mjs`, `docs/SECURITY.md`.
- **Evidence method:** two headless probes over the built output, both exit-code checkable, no screen taken. `csp-probe.mjs` loads all 8 routes and collects `securitypolicyviolation` events plus CSP console errors; `csp-injection.mjs` splices the AUDIT-0009 beacon and an inline script into a built page and compares behaviour with the policy present against the same page with it stripped out.
- **Proof classification:** machine-verifiable.
- **Required checks:** `npm run build`; `npm run check`; `npm test`; `python3 scripts/validate-governance.py`; deploy-time Lighthouse a11y gate (≥0.95).
- **Rollback/containment:** one config block; `git revert -m 1`.
- **Issue links:** AUDIT-0010, AUDIT-0009. No GitHub issue.
- **Evidence after completion:** All 8 routes carry the policy and report **0 violations**. Gates: build exit 0, check 0/0/0, 83/83 tests, validator 44 checks passed.

  **The probe caught a defect this card would otherwise have shipped.** The first run failed 4 of 8 routes on `style-src-attr`, and what was blocked is how the Spectrum identity works — `--hue` is set per band as a style attribute (`index.astro`, `ProductBand.astro`, `apps/[slug].astro`), so every product colour on the site would have silently reverted to the achromatic default:

  | Route | First run | After `styleDirective` |
  |---|---|---|
  | `/` | FAIL — 3 style-src-attr violations | PASS, `--hue=#ff9245` |
  | `/apps/` | FAIL — 1 | PASS, `--hue=#ff9245` |
  | `/apps/sole-focus/` | FAIL — 3 | PASS, `--hue=#ff9245`, gallery working |
  | `/privacy/sole-focus/` | FAIL — 1 | PASS |
  | `/about/`, `/support/`, `/privacy/`, `/404` | PASS | PASS |

  Hashes cannot fix it: the spec excludes style attributes from hash matching unless `'unsafe-hashes'` is set, and the hue varies per product. Astro documents `{ resource: "'unsafe-inline'", kind: "attribute" }` for exactly this case. A first attempt putting `style-src-attr` in `directives` was rejected by Astro's own schema validation, which named the correct field — the tooling refusing the wrong shape is what pointed at the right one.

  **The negative test, with a control:**

  | | Inline injection ran | Beacon requested |
  |---|---|---|
  | Same page, policy stripped out | **yes** | **yes** |
  | Same page, policy in place | no | no |

  The control is the point: a policy nobody has seen block anything is a meta tag, not a control. The gallery was driven as well as loaded — the arrow is visible only once the inline module runs, and clicking it advanced the counter.

  **Known and accepted:** `style-src-attr 'unsafe-inline'` is a real widening, scoped to style attributes alone. It cannot execute code, and the CSS-exfiltration attacks it theoretically enables need an injection point this site does not have — no user input, no forms, no query handling. `frame-ancestors`, `report-uri` and report-only mode are unavailable in a meta element; HSTS, `referrer-policy` and `x-content-type-options` still absent because GitHub Pages cannot set headers. All of it is recorded in `docs/SECURITY.md`, with Cloudflare Transform Rules named as the owner's route to real headers.

  **Not proved locally:** the Lighthouse accessibility gate. It cannot run on this machine; `.github/workflows/deploy.yml` runs it on every deploy and blocks below 0.95. The headless probe loaded all 8 routes with zero console errors, which covers the rendering risk this change actually carries.
