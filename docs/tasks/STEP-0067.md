# Task Card — STEP-0067

- **ID:** STEP-0067
- **Type:** refactor (Open/Closed — content ownership)
- **One outcome:** A product's privacy wording can change without editing a shared component.
- **Feedback:** AUDIT-0010, which ranked this the highest-value refactor in the codebase. Open follow-up #2 from the 2026-07-18 health check.
- **Why now:** `PolicyArticle.astro` held the prose for five legal sections as literal strings — "How your data is protected" behind ternaries on `storedLocally` / `dataCollected`, plus "Children's privacy", "Your rights", "Contact & requests" and "Changes to this policy". A product whose legal text differs — anything with accounts, anything collecting data — meant editing a component every product renders through. `docs/SECURITY.md` already warns that a real app's policy must be truthful to that app's actual practices; this structure stood in the way of that, and legal text is the worst possible thing to have to change in a shared place.
- **Prior art:** none sought. This applies the project's own established pattern — content collections with a zod schema (`src/content/schema.ts`) — to text it did not yet cover. No search knows this schema.
- **Avoid:** making the sections required schema fields. Both existing policies would have to restate boilerplate that is already correct for them, and `retention` already fails the build when missing — more required fields means more ways to be blocked on wording nobody wants to change, which is how a policy ends up wrong.
- **Avoid:** letting an override carry the contact address. Apple 5.1.1(i) requires the page to offer a deletion/contact route; if the address lives inside overridable prose, a content edit can drop it silently.
- **Approach:** move the generated wording into `src/lib/policy-text.ts` as pure functions of the policy's own facts, add an optional `sections` object to `privacyPolicyEntrySchema`, and resolve override-or-default through one function. The component now decides where text goes and never what it says.
- **Design decision — override, not replace.** The ternaries produce genuinely correct default wording for the common case. Deleting them would force every future product to hand-write five sections of legal prose.
- **Design decision — `resolveSection` ties both branches.** Without it, overridden prose would be the one text on the site exempt from the wrapping rule (STEP-0062).
- **Design decision — the address is appended by the component.** "Your rights" and "Contact & requests" defaults deliberately end mid-sentence, so the contact route cannot be overridden away.
- **Acceptance criteria:** (1) No literal legal prose left in `PolicyArticle.astro`. (2) Setting an override changes only that section, in only that policy. (3) Both published policies render the same text as before. (4) Schema and default-text coverage in tests.
- **Non-goals:** rewriting any published policy text; changing the visual design of the policy page.
- **Files:** `src/content/schema.ts`, `src/lib/policy-text.ts` (new), `src/lib/policy-text.test.ts` (new), `src/components/PolicyArticle.astro`, `src/lib/privacy.test.ts`.
- **Evidence method:** both policy pages rebuilt and compared against a saved baseline, normalised for entity encoding and non-breaking spaces; plus a real end-to-end override written into `sole-focus.md`, built, measured across both pages, and reverted.
- **Proof classification:** machine-verifiable.
- **Required checks:** `npm run build`; `npm run check`; `npm test`; `python3 scripts/validate-governance.py`.
- **Rollback/containment:** `git revert -m 1`. The schema field is optional and defaults to `{}`, so reverting cannot orphan content.
- **Issue links:** AUDIT-0010. No GitHub issue.
- **Evidence after completion:** No literal legal prose remains in the component (0 matches for any of the five sections' opening phrases). Gates: build exit 0, check 0 errors / 0 warnings / 0 hints, **96/96 tests** (83 before; 13 added), validator 44 checks passed.

  **The override, proved end to end.** A temporary `sections.children` override was written into `sole-focus.md`, built, and measured on both policy pages, then reverted:

  | Section | Site-wide policy | Sole Focus policy |
  |---|---|---|
  | The override text | absent | **present** |
  | The default children's text | **present** | replaced |
  | Protection, rights, contact, changes | unchanged | unchanged |

  One section, one policy, nothing else — which is the whole claim of the card.

  **Not byte-identical, and the difference is an improvement.** The published text is the same, but two things changed:

  1. **Four sections now get the wrapping rule.** Only "Your rights" called `tie()` before; the other four were raw JSX text and were the last body copy on the site exempt from STEP-0062. Routing everything through `resolveSection` closed that. This accounts for every non-breaking space in the diff.
  2. **A missing space is now present.** "Questions, consent changes, or deletion requests —" ran flush against the support address in the built HTML, because JSX collapsed the newline that was standing in for the space. Now `— ` is explicit. One character, and it was a real defect.

  Normalised for entity encoding and non-breaking spaces, that single space is the *only* text difference across both pages.

  **Two dead ends worth recording.** An intermediate build failed with `Cannot read properties of undefined (reading 'protection')`, which looked like the schema default not applying. It was not: a probe test proved `sections` parses to `{}` correctly. The cause was the content-layer cache — and clearing `.astro` does nothing, because the cache lives in **`node_modules/.astro/data-store.json`**. Anyone changing a collection schema here will hit the same thing; a fresh CI build has no cache and is unaffected. Separately, three new tests failed on first run because their expectations ignored `tie()`; the code was right and the tests were wrong, and they now assert the tied form, which is what actually ships.
