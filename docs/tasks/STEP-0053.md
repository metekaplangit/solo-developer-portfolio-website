# Task Card — STEP-0053

- **ID:** STEP-0053
- **Type:** feature (UI polish — image loading and sizing)
- **One outcome:** The one image that is the largest thing on a page's first screen is fetched at high priority, and every `sizes` attribute declares the slot the layout actually gives it.
- **Why now:** Measured 2026-07-31 — the hero screenshot was `loading="eager"` with no priority hint, and the home mosaic declared `40vw` (576px at 1440) for a slot that renders **604px**, so the browser was choosing a variant one step too small. Fourth and last polish card.
- **Prior art:** `fetchpriority="high"` on the single LCP element is the supported, browser-native way to raise it, and it must be used on **exactly one** image per page — marking everything high is the same as marking nothing high. Reported LCP improvements of 20–30%; Baseline in every major browser as of 2026 (web.dev, *Optimize resource loading with the Fetch Priority API*; Addy Osmani, *Use fetchpriority=high to load your LCP hero image sooner* — both checked 2026-07-31). Followed.
- **Avoid:** adding `<link rel="preload">` as well. The image is discoverable in the markup, so the sources say a preload on top of the attribute adds a second mechanism for little further gain here. Also avoid marking the gallery's slides 2–5 — the same sources are explicit that only the first slide of a carousel should be eager or prioritised.
- **Design decision — the prop carries both, so they cannot drift apart.** `ProductBand`'s existing `eager` prop now sets `loading="eager"` **and** `fetchpriority="high"` together, and only the first band on a page passes it. A separate `priority` prop would have allowed a band that is eager but not prioritised, or worse, prioritised but lazy.
- **Design decision — the product page's LCP is the gallery's first slide, not a band.** That page has no `ProductBand`, so the hint goes on `ScreenshotShowcase`'s `i === 0` slide, which already had `loading="eager"`.
- **Non-goals:** image quality settings, format changes, a preload, the favicon/OG artwork.
- **Files:** `src/components/ProductBand.astro`, `src/components/ScreenshotShowcase.astro`, `src/pages/index.astro` (mosaic `sizes` and `widths`).
- **Evidence method:** measured `naturalWidth` of the chosen variant against the rendered CSS width for every raster image on every route, with lazy images forced to load and decoded first; plus a per-page count of `fetchpriority="high"`.
- **Proof classification:** machine-verifiable (measured).
- **Required checks:** `npm run build`; `npm run check`; `npm test`; validator; deploy-time Lighthouse a11y gate (≥0.95).
- **Byte cost, stated rather than hidden:** the build grew from **1.4MB / 42 WebP variants to 1.5MB / 46** — four new 1400w variants for the mosaic. A DPR-1 visitor's bytes rise slightly too (a 604w variant instead of a 576w one), because 576 was the wrong answer: it was being upscaled into a 604px slot. A DPR-2 Retina visitor — which is this audience — gets a variant that actually covers the slot. That is the trade, and it is the point of the card.
- **Issue links:** Owner UI-polish request, 2026-07-31. Follows STEP-0052; closes the UI-polish phase (STEP-0050..0053).
- **Rollback/containment:** attribute-level changes in three files; `git revert -m 1`.
- **Evidence after completion:** `fetchpriority="high"` appears **exactly once** on `/`, `/apps/` and `/apps/sole-focus/`, and **zero** times on the four pages with no above-the-fold image — counted in the built HTML. Every raster image on all three image-bearing routes now picks a variant **at least as wide as its rendered slot** (11 images checked, 0 undersized; the home mosaic went from 576 chosen for a 604 slot to an exact 604, and the product page's lead slide from a match to a match at 1152/1150). Gates: build exit 0, check 0-0-0, 61/61 tests, validator pass.
