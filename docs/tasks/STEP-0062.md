# Task Card — STEP-0062

- **ID:** STEP-0062
- **Type:** fix (typography — line wrapping and column evenness)
- **One outcome:** No line of body text ends on a stray short word, anywhere on the site, and the home page's three feature columns are the same length.
- **Feedback:** `2026-08-01-text-line-breaks`, `2026-08-01-feature-paragraphs-uneven`
- **Why now:** The owner reported the home hero breaking after "…a plain privacy page and a", and separately that the three feature columns "are not matching each other". Measured before the fix at 1440 across all eight routes: **22 paragraphs** ended a line on a stray article, preposition or auxiliary, and the columns ran **7, 7 and 4 lines**, the third stopping 74px short of the other two.
- **Prior art:** Chrome's own documentation for `text-wrap: pretty` states it addresses **orphans — the last line of a paragraph** — and adjusts only the final lines; it does not consider where short words fall mid-paragraph ([Chrome for Developers, *CSS text-wrap: pretty*](https://developer.chrome.com/blog/css-text-wrap-pretty)). The established remedy for a stray function word is the non-breaking space, binding it to the word it points at ([24 ways, *Run Ragged*](https://24ways.org/2013/run-ragged/); [UX Movement](https://uxmovement.com/content/why-you-should-remove-orphans-from-your-body-text/)). Checked 2026-08-01. Followed.
- **Avoid:** reaching for CSS. `text-wrap: pretty` was **already applied site-wide** (DESIGN.md §3, the Balanced-Heading Rule) and all 22 defects were present anyway. A session that had not measured would very plausibly have "fixed" this by adding a property that was already there.
- **Avoid:** `markdown.rehypePlugins`. It still works, but on this Astro version it requires installing `@astrojs/markdown-remark`, which switches the Markdown processor for **every file on the site** from Sätteri back to unified. A dependency plus a pipeline swap is a large blast radius for one text transform; Sätteri's native `hastPlugins` does the same job with neither.
- **Avoid:** shortening the product's prose sections to even the home columns. Those same sections are the product page's description, where the length belongs. Truncating with `-webkit-line-clamp` was also considered and rejected: it would have matched the heights exactly and read as a page that ran out of room.
- **Approach:** one rule in `src/lib/typography.ts`, reached three ways — a Sätteri hast plugin for Markdown, one `.transform(tie)` in the content schema for prose fields, and `tie()` at the definition point of the site's own strings. The home columns show `firstSentence()` of each section, with the three openings rewritten to a matching length.
- **Design decision — the rule is a word list, not a length threshold.** "calm", "Mac" and "free" are all short and all perfectly good line endings; what makes a word unusable at a line end is that it points *forward*. Length is only correlated with that, so the list names articles, conjunctions, prepositions, and the auxiliaries ("Each product has / its own policy"). `up`, `off` and `out` are deliberately excluded — as often particles closing a phrase as prepositions opening one.
- **Design decision — a cap on the pair length.** A non-breaking space removes a wrap opportunity, and a long enough unbreakable run overflows a narrow column, which is the one defect this site never accepts. `MAX_PAIR = 22` characters, sized against the ~30-character text column at 320px, and verified there.
- **Two defects the rule could not see until it was measured:** (1) Markdown is hard-wrapped in the source, so "…Each\nproduct has…" reaches the plugin with a real newline. `tie()` deliberately never crosses a newline — in a raw string it is a wrap the author chose — but in HTML the browser collapses it to a space and will break there. Normalised in the plugin, where it is correct to. (2) A text node ends where an element begins: "…and **Study mode**" leaves "and" stranded with no way to see what follows. `tieAcross()` handles the boundary. Neither was predictable by reading; both came from re-measuring after a partial fix.
- **Acceptance criteria:** (1) 0 stray line endings across all 8 routes at 1440. (2) The three home columns render 3 lines each and end at the same y. (3) 0 horizontal overflow at 320 / 390 / 1024 / 1440. (4) No new runtime dependency and no Markdown pipeline swap. (5) Section titles are NOT tied — a heading gets `text-wrap: balance`, and one bound unit cannot balance.
- **Non-goals:** the short grid row (STEP-0063); hyphenation; justified text.
- **Files:** `src/lib/typography.ts` (+ test), `src/lib/satteri-tie.ts`, `src/lib/prose.ts` (+ test), `src/lib/site.ts`, `src/content/schema.ts`, `src/content/products/sole-focus.md`, `src/pages/index.astro`, `src/pages/support/index.astro`, `src/pages/about/index.astro`, `src/components/MakerNote.astro`, `src/components/PolicyArticle.astro`, `astro.config.mjs`.
- **Evidence method:** headless probe over the built `dist/`, walking every prose block's visual line boxes and reporting the trailing word of each line. Exit-code checkable, no screen required.
- **Proof classification:** machine-verifiable (measured line boxes).
- **Required checks:** `npm run build`; `npm run check`; `npm test`; validator; deploy-time Lighthouse a11y gate (≥0.95).
- **Rollback/containment:** `git revert -m 1`. The rule is one module; removing its three call sites restores the previous text exactly, since nothing but spacing changed.
- **Issue links:** Feedback items `2026-08-01-text-line-breaks` and `2026-08-01-feature-paragraphs-uneven`. No GitHub issue. Extends the Balanced-Heading Rule (DESIGN.md §3) rather than replacing it.

  **A caching trap worth recording.** After the schema transform was added, the built HTML did not change and the transform appeared not to run — it did run, provably, in isolation. Astro's content layer had cached the parsed entries in `.astro/` **and** `node_modules/.astro/`; clearing both took the page from 29 non-breaking spaces to 255. A schema change to a content collection is not picked up by a plain `npm run build`.

The padding is deliberate and the difference is not visible; the box positions are identical.
