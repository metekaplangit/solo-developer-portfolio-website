# Task Card — STEP-0058

- **ID:** STEP-0058
- **Type:** perf (image delivery) — **CLOSED: measured and rejected. No product change shipped.**
- **One outcome (proposed):** The largest image on the product page is served as AVIF where the browser takes it, WebP everywhere else.
- **Why it was proposed:** ENH-0007 Finding 4. It was the only remaining measurable byte win on a site that is otherwise already light.
- **Prior art:** Astro's `<Picture>` emits a `<picture>` with `formats={['avif','webp']}` so the browser picks the smallest format it supports, WebP as fallback (Astro Docs, *Images*; *Image and Assets API reference*; checked 2026-08-01). The widely-reported figure is **20-30% smaller than WebP at comparable quality**.
- **Avoid:** switching every image on the site. Astro issue #8866 records `<Picture>` generating unused variants, and AVIF encoding is slow — a site-wide swap buys little and lengthens every build. Scope was one element.
- **What was built and measured:** `<Picture formats={['avif','webp']} fallbackFormat="webp">` on the first gallery slide only (`ScreenshotShowcase.astro`), keeping the existing `widths`, `sizes`, `quality={78}`, `loading="eager"` and `fetchpriority="high"` unchanged. Built clean, emitted a correct `<picture>` on `/apps/sole-focus/` with the AVIF source ordered before WebP.

## The measurement, which refutes the card

Same source image, same four widths, same `quality={78}`, one build:

| Width | WebP | AVIF | AVIF vs WebP |
|---|---|---|---|
| 720 | 12,094 B | 15,823 B | **+30.8%** |
| 1080 | 20,582 B | 25,440 B | **+23.6%** |
| 1440 | 28,614 B | 34,412 B | **+20.3%** |
| 1920 | 40,112 B | 45,881 B | **+14.4%** |

AVIF is **larger at every width**, by 3.7-5.8 KB each. The card's own stated
reject rule was "if the measured saving lands under 10 KB the card closes as
measured-and-rejected"; the saving is negative, so it closes.

- **Why the field's 20-30% figure does not hold here.** That figure is drawn from photographic content. These are application screenshots: flat fills, hard edges, and a great deal of small rendered text. WebP's lossy encoder is strong on exactly that material, and a `quality` number is not comparable between the two codecs. The general claim is not wrong; it is about different pictures.
- **Where source and measurement disagreed, the measurement won.** Every source said AVIF would be smaller. It is not, for this image, at this quality, on this encoder. Nothing was shipped on the strength of the source.
- **Not retried at a different quality.** Lowering AVIF's quality until it wins would compare two different pictures, and raising WebP's for a fair fight changes an image the owner has already accepted. Out of scope for this card; a genuine format review would need a visual comparison, which this machine cannot do.
