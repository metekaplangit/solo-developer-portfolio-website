# Task Card — STEP-0057

- **ID:** STEP-0057
- **Type:** fix (UI motion — scroll-reveal fill mode)
- **One outcome:** A revealed element rises into place instead of jumping 22px down and then rising.
- **Why now:** v0.44.9 set `animation-fill-mode: none` on the strength of a probe that could not scroll. The side effect ships on every reveal, on every page, for every visitor. Found by the ENH-0007 logic review.
- **Prior art:** MDN, *`animation-timeline: view()`* — "If the chosen axis does not contain a scrollbar, then the animation timeline will be inactive (zero progress)." The CSS Scroll-Driven Animations Module Level 1 draft states the same for a subject whose nearest ancestor scroll container has no scrollable overflow. Every practitioner source found recommends `animation-fill-mode: both` for view timelines (Ryan Mulligan, *Starting Exploration of Scroll-driven Animations*; Codrops, *A Practical Introduction to Scroll-Driven Animations with CSS `scroll()` and `view()`*). Checked 2026-08-01. Followed.
- **Avoid:** restoring `from { opacity: 0 }`. With `fill: both` and a genuinely inactive timeline it hides content permanently — the v0.44.8 failure mode, and exactly what `DESIGN.md` §6 forbids. The fade stays deleted. That rule is right even though the measurement that triggered it was not.
- **Avoid:** trusting any further reading of this from a headless pane on this machine. Re-measured on the live site 2026-08-01: `innerHeight: 0`, `scrollY` frozen at 0 across six `scrollTo` calls, `timeline.currentTime` null on all five `.reveal` elements, `CSS.supports('animation-timeline','view()')` true. A zero-height viewport has no block-axis scrollbar, so by the rule above every ViewTimeline on the page is inactive and reports progress 0 — which is the whole of the evidence v0.44.8 and v0.44.9 were written against.
- **Design decision — `both`, not `none`.** With `none` the animation contributes nothing before `entry 5%`, so the element renders at its FINAL position and then jumps 22px down the instant the range opens. `both` holds the nearer keyframe outside the range, which is a rise. The residual risk of `both` — an element left 22px low where the timeline never activates — is the tradeoff v0.44.8 already accepted and wrote down, and it is bounded because the keyframes carry no opacity.
- **Acceptance criteria:** (1) `.reveal` computes `animation-fill-mode: both` in the built CSS. (2) `@keyframes reveal-rise` contains no `opacity`. (3) The `@supports (animation-timeline: view())` and `prefers-reduced-motion: no-preference` guards are unchanged. (4) No JavaScript added. (5) 0 horizontal overflow.
- **Non-goals:** restoring the fade; changing the `animation-range`; the `sibling-index()` stagger rewrite (support is not there — see ENH-0007).
- **Files:** `src/styles/global.css` (the `.reveal` rule and its comment block).
- **Evidence method:** grep the built CSS in `dist/` for the computed `animation-fill-mode`, for `opacity` inside `@keyframes reveal-rise`, and for both guards. Exit-code checkable; no screen required.
- **Proof classification:** machine-verifiable (structural), with appearance recorded **unproven** below.
- **Required checks:** `npm run build`; `npm run check`; `npm test`; validator; deploy-time Lighthouse a11y gate (≥0.95).
- **Unproven, stated rather than rounded up:** what the reveal looks like. No harness on this machine can observe a scroll-driven animation mid-range — the same limitation STEP-0055 and STEP-0056 recorded, and the same limitation that produced the reading this card undoes. **Watch it on the live site after deploy.** One word is the whole rollback.
- **Issue links:** ENH-0007 Finding 1 (`docs/enhancements/ENHANCEMENT_ENH-0007.md`). Follows STEP-0056 and the v0.44.8/v0.44.9 hotfixes.
- **Rollback/containment:** one declaration in one rule; `git revert -m 1`.
