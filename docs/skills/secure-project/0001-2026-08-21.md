# Security gate — 2026-08-21

## Verdict

**Safe to publish.** Nothing an attacker can reach through the site itself was
found: no secrets anywhere, no injection surface, no client-side URL handling, no
stored data, and a live page byte-identical to the build except for two HTML
comments the edge strips.

Three things clear the bar. One was fixed in this run (v0.50.2). **Two are outside
this repository and only the owner can close them** — they live in the Cloudflare
dashboard, and neither can be fixed from code, because GitHub Pages cannot set
headers and Cloudflare sits in front of it.

The product is safe to publish. The *domain* is one setting short of safe.

## What this is

A static Astro site (`output: 'static'`) published to GitHub Pages behind a
Cloudflare-proxied custom domain. It is a shop window: it describes two Mac apps,
sends visitors to the App Store, publishes a privacy page per product, and prints
one support address. It holds nothing, stores nothing, and asks for nothing —
no accounts, no forms, no cookies, no localStorage, no service worker, no backend.

**In:** nothing. No user field, no query parameter, no upload, no deep link handled.
**Out:** three external destinations only — two App Store URLs and one GitHub
profile, all `rel="noopener"`.

## Attackers this run chose

- **A network attacker** — café Wi-Fi, a hostile ISP, a rogue access point. Visitors
  arrive by typing a domain, so the first request is theirs to answer.
- **An impersonator** — the site publishes `support@metkapstudio.com` and its whole
  purpose is persuading people to download software.
- **A supply-chain attacker** — 686 packages build an artifact that publishes
  straight to the live domain with `pages: write`.
- **An infrastructure hijacker** — DNS, the Pages custom-domain binding, certificate
  issuance.

Ruled out in writing, so the skip is visible:

- **An authenticated user** — there are no accounts, sessions or roles.
- **A malicious input** — no forms, no query handling, no server. Verified: zero
  `location.*` reads, zero `searchParams`, `form-action 'none'`, the only `set:html`
  uses are a JSON-LD blob with `<` escaped and two literal HTML comments.
- **A local attacker on the visitor's device** — the site stores nothing at all.
- **An insider with backend access** — there is no backend.

### On finding 1

This is the one that matters most, and it is worth being precise about why. GitHub's
API reports `https_enforced: true` for this Pages site, and general knowledge says
GitHub Pages sends HSTS when HTTPS is enforced. Measured against the live domain on
2026-08-21, no HSTS header arrives — not through Cloudflare and not straight at
`185.199.108.153`. The measurement was followed over the general rule.

The damage is specific to what this site is for. Every page carries a Download
button; the site exists to move people from a URL they typed to a binary they
install. An attacker who owns the first plaintext request serves their own page at
the right domain, in the right design, with their own download link.

### On finding 3

Neither advisory was reachable: nothing runs after the build on a static site, and
the only YAML the build parses is frontmatter the owner wrote. What was actually
broken is that a control this project wrote down as merge-critical had no command
behind it. `npm run audit` now runs first in the `headless` chain, strict, on every
card. Seen red against the unfixed tree before it was trusted.

## Below the bar — recorded, not worked

- **The domain is not verified with GitHub.** No `_github-pages-challenge-metekaplangit`
  TXT record exists. Not reachable today; it becomes a full-domain takeover the day
  Pages is ever unlinked, renamed or deleted. `docs/DEPLOYMENT.md` already recommends it.
- **No DNSSEC.** `dig DS metkapstudio.com` is empty. `docs/DEPLOYMENT.md` says to enable it.
- **No CAA record.** Any certificate authority may issue for this domain.
- **The Cloudflare proxy is ON, and `docs/DEPLOYMENT.md` documents it OFF.** The A
  records are `104.21.50.131` / `172.67.163.61`, not GitHub's `185.199.x`. The edge is
  actively rewriting HTML right now — the live page differs from `dist/index.html` by
  exactly the two `<!--email_off-->` comments, which it consumes. This is the
  AUDIT-0009 injection channel, open again. It is contained rather than closed: the
  `<meta http-equiv>` CSP survives the edge intact, and `script-src 'self'` plus
  hashes would block an injected beacon. The support address renders live, so the
  obfuscation defence is doing its job.
- **10 dev-only advisories** in `@lhci/cli@0.15.1`'s ageing tree (`inquirer`,
  `external-editor`, `tmp`, `uuid`). Left alone deliberately: `npm audit fix --force`
  resolves them by installing `@lhci/cli@0.1.0`, which would remove the blocking
  accessibility gate from the deploy workflow. That trade makes the product worse.
- **Workflow actions are pinned by tag, not commit SHA** (`actions/checkout@v7` and
  four others). All are first-party GitHub-owned actions.
- **`access-control-allow-origin: *`** on every response. GitHub Pages' default; the
  site is entirely public, carries no credentials and exposes no API.

## What was checked and found clean

- **Secrets:** none in the working tree, none in the built `dist/`, none anywhere in
  the full `git log --all -p` history, and no sensitive filename was ever tracked.
  No `.env` file exists.
- **Build output:** no source maps, no `.ts`, no dotfiles. 10 HTML, 3 CSS, images, and
  the sitemap — nothing unintended. `/_astro/` and `/.git/config` both 404 live.
- **Lockfile:** every package has an integrity hash, every `resolved` points at
  `registry.npmjs.org`, and exactly 2 packages carry install scripts (`esbuild`,
  `fsevents`).
- **Injection surface:** none. No `innerHTML`, no `eval`, no `new Function`, no
  `document.write`. The one inline script is the screenshot gallery and it reads no URL.
- **Live vs built:** byte-identical except the two stripped comments.
- **CSP:** the full policy arrives intact on the live page, with real per-asset hashes.
- **astro 7.1.6:** no advisory against it in the GitHub Advisory Database as of 2026-08-21.

## What could NOT be checked

- **The Cloudflare dashboard.** No API token is available here, and its settings are
  not this run's to change. Email Obfuscation, Rocket Loader, the SSL/TLS mode
  between Cloudflare and GitHub, and any WAF or transform rule are all unverified.
- **The Gmail inbox** that `support@metkapstudio.com` forwards to.
- **The two App Store listings** the download buttons point at.
- **Whether GitHub's "Enforce HTTPS" ever reaches a browser.** The API says it is on;
  no header proves it. Cloudflare is in the path.

## What the owner must do

1. **Turn on HSTS** — Cloudflare dashboard → SSL/TLS → Edge Certificates → HTTP Strict
   Transport Security. Start at 6 months, `includeSubDomains` off until mail and any
   subdomain are known good. This closes finding 1 and nothing else can.
2. **Move DMARC off `p=none`** — Cloudflare → DNS → the `_dmarc` TXT record →
   `v=DMARC1; p=quarantine; rua=mailto:…`, then `p=reject` after a fortnight of clean
   reports. Safe here: `docs/DEPLOYMENT.md` records that nothing sends *from* the
   domain — replies go from the Gmail — so no legitimate mail can be caught.
3. **Verify the domain with GitHub** — user Settings → Pages → Verify a domain, then
   add the `_github-pages-challenge-metekaplangit` TXT record at Cloudflare.
4. **Enable DNSSEC** — Cloudflare → DNS → Settings. Already in `docs/DEPLOYMENT.md`
   as intended and never done.
5. **Add a CAA record** — Cloudflare → DNS, `0 issue "letsencrypt.org"` and
   `0 issue "pki.goog"`, so only GitHub's and Cloudflare's CAs may issue.
6. **Decide about the Cloudflare proxy.** It is on; the deployment doc says it should
   be off. Either turn it off, or correct the doc's intent and accept that the edge
   rewrites HTML — with the CSP as the thing that keeps that honest.

No key needs rotating: there are none.
